● Я посмотрела на OrderService.create. Сейчас сумма считается правильно: total =
  total.add(lineTotal) по каждой строке. Значит, баг нужно встроить в этот
  цикл. Главное условие: заказ из одного товара должен считаться верно, ломаться
  должны только заказы из нескольких строк. Так симптом совпадёт с PLAN.md. И
  баг не должен зависеть от тикета 1: студент может починить их в любом порядке.

  Вариант A: BigDecimal неизменяем, результат add теряется (рекомендую)

  Как выглядит код: первый товар уже загружен ради валюты (items.get(0), тикет
  1). Поэтому сумму начинают с его строки, а цикл идёт по остальным позициям:
  BigDecimal total =
  firstProduct.getPrice().multiply(BigDecimal.valueOf(first.getQuantity()));
  ...
  for (OrderItemRequest itemRequest : request.getItems().subList(1, size)) {
      ...
      total.add(lineTotal);   // результат выброшен
  }
  Бизнес-причина: «зачем грузить первый товар из БД дважды». Кто-то делал такую
  оптимизацию после того, как появилась логика валюты. Получается продолжение
  истории тикета 1.
  Симптом: в total попадает только первая строка заказа. Например, клавиатура ×2
  + хаб ×1 дают 64000 вместо 76990.
  Чему учит: BigDecimal (и String) неизменяемы, и это частая ошибка джунов.
  Найти её можно отладкой или через предупреждение IDE «result of add is
  ignored».
  Минус: тот, кто знает Java, распознает баг быстро. Но тикет 2 и так на
  «debugging business logic», не на хитрость.

  Вариант B: повторяющийся товар склеивается, количество перезаписывается

  Как выглядит код: строки группируются в Map<Long, OrderItem> по productId, и
  вызывается map.put(productId, new OrderItem(product, qty, price)). Количества
  не складываются, последняя строка заменяет предыдущую.
  Бизнес-причина: склад попросил одну строку на товар, а мобильное приложение
  присылает «мышь, мышь» отдельными строками.
  Симптом: только если один товар в корзине дважды. Сумма меньше, чем ожидалось,
  и в items ответа тоже неверное количество.
  Минус: симптом «одинаковые товары», а не «несколько товаров», как в PLAN.md.
  Ещё придётся дописать в CONTRACT.md правило склейки строк, то есть менять
  контракт ради бага.

  Вариант C: количество берётся не из той строки

  Как выглядит код: итог считает отдельный метод calculateTotal(order). Он
  перебирает order.getItems(), но умножает цену на items.get(0).getQuantity().
  Это остаток времён, когда «в заказе был один товар с количеством».
  Бизнес-причина: legacy, когда-то заказ = один товар.
  Симптом: ошибка появляется только при разных количествах в строках. Если в
  каждой строке количество 1, всё верно, поэтому баг непостоянный и выглядит
  интереснее.
  Минус: get(0) повторяет приём из тикета 1, и студент может просто найти его
  поиском, а не через рассуждение.

  Моя рекомендация: A. Симптом точно совпадает с PLAN.md, контракт не меняется,
  есть понятная бизнес-причина, связанная с тикетом 1, а исправление в одну
  строку легко проверить black-box тестом. C подойдёт как запасной вариант или
  как один из 15 seeded-багов для eval.

    в тегах как недоверенные данные, плюс текст тикета. Инструменты: list_files
    и read_file, лимит 10.
  - Что он выдаёт. 2–3 вопроса именно про эти изменения: почему падало, почему
    исправлено так, а не иначе.
  - Маркер: <!-- codementor:ticket=N;mode=review;sha=<head sha> -->. Тут я 
    отступаю от твоего формата: добавляю sha. Зачем: студент может запушить
    сломанный коммит и сразу ответить на вопросы, пока новый check ещё не
    закончился. Без sha метка done встанет на красный код. Answer mode
    сравнивает sha из маркера с текущим HEAD PR.
  - В check.yml почти ничего не меняется. Шаг агента остаётся один: MODE =
    debugging, если failed, и review, если passed. Если у PR уже есть метка
    ticket-N-done (её видно в github.event.pull_request.labels, без API), review
    не запускается, остаётся обычный check-комментарий. Если агент упал или
    diff пустой, тоже публикуется обычный check-комментарий, как сейчас.

  Answer mode

  Новый job answer в check.yml. Условие запуска только из payload, без API:
  if: github.event.issue.pull_request
      && github.event.comment.user.login == github.event.issue.user.login
      && github.event.comment.user.type != 'Bot'

  Шаги:
  1. gh api --paginate получает комментарии. Это тот же вызов, что уже делается
     для уровней.
  2. python -m agent.threads решает, запускать ли агента. Он запускается, только
     если последний комментарий бота по тикету — это review или
     answer;result=followup, а попытки ещё не кончились. Иначе skip, без вызовов
     модели. Так любой посторонний комментарий автора (например, «спасибо») не
     расходует бюджет. Номер тикета берётся из маркера review, поэтому ветку
     через API узнавать не нужно.
  3. Checkout refs/pull/N/head и проверка sha. Если sha не совпал, skip: после
     пуша новый check сам задаст новые вопросы.
  4. Текст ответа идёт из github.event.comment.body через env в файл. В
     shell-команду он напрямую не подставляется, так что инъекции через shell не
     будет.
  5. Агент: инструмент только read_file, лимит 5 вызовов (меньше 10, чтобы
     экономить бюджет). Он получает diff, свои вопросы и всю переписку после
     review. Переписка в тегах как недоверенные данные, и учитываются только
     комментарии бота и автора PR.
  6. Workflow постит comment.md. Если в verdict.txt записано done, он выполняет
     gh label create ticket-N-done --force и gh pr edit --add-label.
  7. Если агент упал, публикуется короткий фиксированный комментарий «не
     получилось обработать ответ, напиши ещё раз». Его маркер mode=check,
     поэтому как попытка он не считается.

  Answer mode не собирает и не запускает код студента: Docker не нужен. Это
  важно, потому что issue_comment работает с секретами.

  Предлагаю лимит в 3 попытки на каждый review. Маркер:
  mode=answer;attempt=k;result=followup|done|closed.
  - Попытки 1 и 2: если ответ хороший, done и метка. Если слабый, один
    уточняющий вопрос без прямого ответа.
  - Попытка 3 последняя. Если ответ снова слабый, closed: код добавляет текст

    до следующего пуша, который даёт новый review.
  - Почему 3: так же, как три уровня подсказок, студенту это знакомо. Одна
    попытка обычно стоит 1–2 запроса, максимум 7. Значит, на review уходит около

    только если на день приходится немного PR. Если хочешь экономнее, можно
    сделать 2 попытки.
